**Goal:** Close the three backlog items that are gaps in the quality gates themselves, prove the definition-of-done's first line both by hand and in CI, state what 1.0.0 commits to, and tag the release.

**Architecture:** No new subsystems and no new features. ## Global Constraints

- **Python is the worktree-local venv**: `../.venv/bin/python` from `backend/`. The repo-root `.venv` is installed editable against the MAIN checkout — using it silently tests the wrong code.
- **Backend tests (SQLite lane)**: `cd backend && TMPDIR="$HOME/tmp" ../.venv/bin/python -m pytest -q`. Run `mkdir -p "$HOME/tmp"` first — this Mac runs Docker via Colima, which mounts only `$HOME`; without `TMPDIR` the 9 `[docker]` params fail misleadingly.

- **mypy is a gate**: `cd backend && ../.venv/bin/python -m mypy` must stay `Success`, exit 0.
- **Frontend**: `cd frontend && npm test && npm run typecheck`.
- **The bar is 0 failures, 0 skipped, 0 warnings, on BOTH lanes.** A skip is a retired assertion, not a pass.
- **Baseline at the start of this phase: 1038 backend (both lanes), 58 frontend, mypy clean on 96 source files.**
- **No test may reach the network.** A local Postgres container is the system under test, not the network.
- **Every fix gets a test that FAILS without it, verified by mutation. Run mutations over the whole test FILE, never a `-k` filtered subset** — a filtered run under-reported a defect's severity in v0.10.0. **Report the OBSERVED output, never the predicted one.**

**Files:**
- Modify: `backend/ley_khaa/config.py`
- Modify: `backend/tests/test_ollama_config.py`
- Modify: `backend/tests/test_vision_config.py` (eight reload sites)
- Test: `backend/tests/test_settings_env.py` (create)

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: `_env_str(name: str, default: str) -> str`, `_env_int(name: str, default: int) -> int`, `_env_bool(name: str, default: bool, *, false_value: str) -> bool` in `ley_khaa.config`. `Settings()` re-reads the environment on every construction. `ley_khaa.config.settings` remains a module-level singleton built once at import.

**The defect:** `importlib.reload(ley_khaa.config)` rebinds `ley_khaa.config.settings` to a new object. Modules that did `from ..config import settings` before the reload keep the old one, so `test_api.py` (which imports `settings` inside the test body, getting the new object) raises the debounce while `api/app.py`'s `build_orchestrator` reads the old object and builds `ReadinessGate(0)`. The candidate promotes at ingest and the assertion fails. **The backlog's proposed fix — "build a `Settings()` from a patched environment" — cannot work as written**, because the dataclass defaults are evaluated at import; a fresh `Settings()` never re-reads the environment. That is why the test reaches for `reload`.

```python
Two properties, and the second is a rule this project states and did not keep.

1. `Settings()` re-reads os.environ on every construction. Before v1.0.0 the
   dataclass defaults were evaluated once, at class-definition time, so the only
   way to observe a changed variable was `importlib.reload(ley_khaa.config)` —
   which rebinds the module-level `settings` and leaks that new object into every
   later test (backlog item 25).

   the default. `docker-compose.yml` passes `${VAR:-}`, which SETS the variable to
```

```python
def _env_str(name: str, default: str) -> str:
    """A string setting, read at call time and falsy-safe.

    `os.getenv(name, default)` is wrong here: docker-compose.yml passes
    `${VAR:-}`, which SETS the variable to the empty string rather than leaving
    it unset, so the two-argument form returns "" and the default never fires.
    """
    return os.getenv(name) or default


def _env_int(name: str, default: int) -> int:
    """An int setting, read at call time and falsy-safe.

    Deliberately NOT tolerant of a non-integer: `int("lots")` raises during
    import, which is the right posture for a setting whose wrong value would
    silently change behaviour. `_tolerant_int` documents the one exception.
    """
    return int(os.getenv(name) or default)


def _env_bool(name: str, default: bool, *, false_value: str) -> bool:
    """A tri-state flag: unset or "" means the default, `false_value` means False.

    Kept explicit rather than parsing a general truthy set, because the two flags
    that use it have opposite defaults and opposite spellings — LEY_KHAA_VISION
    defaults ON and is disabled by "off"; LEY_KHAA_DISABLE_STARTUP defaults OFF
    and is enabled by "1".
    """
    raw = os.getenv(name)
    if not raw:
        return default
    return raw != false_value
```

```python
@pytest.fixture
def migration_url(tmp_path):
    """An empty database for one migration test, on whichever lane is running.

    Migration tests CREATE tables, so they need a namespace of their own — they
    cannot share `ley_khaa_test`, which `_clean_database` truncates but does not
    drop. On SQLite that is a tmp_path file. On Postgres it is a throwaway schema
    dropped at teardown, with search_path set through the URL's libpq `options`
    parameter so Alembic (which is handed only a URL) creates everything inside
    it — including its own `alembic_version` table.

    Before v1.0.0 these tests hardcoded SQLite URLs, so migrations never ran
    against Postgres at all (backlog item 26) — and `0006_alias_jsonb`'s
    alter_column between JSON and JSON().with_variant(JSONB, "postgresql") is
    invisible on SQLite, where the two render identically.
    """
    if not POSTGRES:
        yield f"sqlite:///{tmp_path / 'migration.db'}"
        return

    schema = f"ley_khaa_mig_{uuid.uuid4().hex[:12]}"
    bootstrap = create_engine(DATABASE_URL, future=True, isolation_level="AUTOCOMMIT")
    try:
        with bootstrap.connect() as conn:

    finally:
        with bootstrap.connect() as conn:
            conn.execute(text(f"DROP SCHEMA IF EXISTS {schema} CASCADE"))
        bootstrap.dispose()
```

- [ ] **Step 1: Write the failing test**

Create `backend/tests/test_lane_guard.py`:

```python
"""The `--database` guard's own test (backlog item 28).

The guard raises pytest.UsageError from pytest_configure, so it cannot be
exercised in-process: by the time a test body runs, the guard has already
decided. These drive a real pytest in a subprocess instead, which is also the
only way to observe the exit code CI actually sees.

Why the guard exists: dropping or misindenting the `env:` block on CI's
`pytest (postgres)` step removes DATABASE_URL, so the step silently re-runs the
SQLite lane and reports a second green. Any check keyed on DATABASE_URL cannot
catch that — the malformation removes the variable the check reads — so the
expectation lives on the command line.
"""

import subprocess
import sys
from pathlib import Path

import pytest

BACKEND = Path(__file__).resolve().parent.parent

# pytest's own exit code for a usage error (pytest.ExitCode.USAGE_ERROR).
USAGE_ERROR = 4

POSTGRES_URL = "postgresql+psycopg://ley:ley@localhost:55432/leykhaa"


def _run(args, env_overrides):
    """Run pytest in a subprocess with a controlled DATABASE_URL.

    `-x --collect-only` keeps a passing invocation cheap; neither flag can mask
    the guard, which fires in pytest_configure before either takes effect.
    """
    import os

    env = dict(os.environ)
    env.pop("DATABASE_URL", None)
    env.update(env_overrides)
    return subprocess.run(
        [sys.executable, "-m", "pytest", "--collect-only", "-q", *args],
        cwd=BACKEND,
        env=env,
        capture_output=True,
        text=True,
    )


def test_asking_for_postgres_on_the_sqlite_lane_is_a_usage_error():
    result = _run(["--database=postgres", "tests/test_lane_guard.py"], {})

    assert result.returncode == USAGE_ERROR, result.stdout + result.stderr
    assert "--database=postgres was asked for, but this run is on sqlite" in (
        result.stdout + result.stderr
    )
    # The remedy has to name the fix, not just the problem.
    assert "set DATABASE_URL to a postgresql+psycopg:// URL" in (result.stdout + result.stderr)


def test_asking_for_sqlite_while_a_postgres_url_is_set_is_a_usage_error():
    """The inverse leak: a DATABASE_URL escaping into the SQLite step."""
    result = _run(["--database=sqlite", "tests/test_lane_guard.py"], {"DATABASE_URL": POSTGRES_URL})

    assert result.returncode == USAGE_ERROR, result.stdout + result.stderr
    assert "--database=sqlite was asked for, but this run is on postgres" in (
        result.stdout + result.stderr
    )
    assert "unset DATABASE_URL" in (result.stdout + result.stderr)


def test_a_matching_lane_is_allowed_through():
    """The guard must not fire when the lane matches — otherwise it would be
    'always fails', which pins nothing and would break CI."""
    result = _run(["--database=sqlite", "tests/test_lane_guard.py"], {})

    assert result.returncode == 0, result.stdout + result.stderr


def test_omitting_the_flag_infers_the_lane_and_never_fails():
    """The SQLite lane stays zero-configuration: bare pytest needs no flag."""
    result = _run(["tests/test_lane_guard.py"], {})

    assert result.returncode == 0, result.stdout + result.stderr
```

```yaml
  compose-smoke:
    runs-on: ubuntu-latest
    # Spec §11's first line — "fresh clone -> docker compose up -> dashboard
    # live" — was last verified by hand at v0.1.0. A claim with a timestamp
    # rots; this is the same line as a mechanism. It runs against the checkout,
    # which is what a visitor's clone gives them.
    steps:
      - uses: actions/checkout@v4

      # No ANTHROPIC_API_KEY is set, deliberately: this is the zero-account
      # demo path a first-time visitor gets, and it must work without one.
      - name: Bring the stack up

      # Only the `db` service declares a healthcheck, so the backend and the
      # dashboard are polled here rather than waited on by compose.
      - name: Wait for the backend to answer
        run: |
          for i in $(seq 1 60); do
            if curl -fsS http://localhost:8000/health > /dev/null; then
              echo "backend healthy after ${i}s"; exit 0
            fi
            sleep 1
          done
          echo "backend did not answer /health within 60s"; exit 1

      - name: Wait for the dashboard to serve
        run: |
          for i in $(seq 1 60); do
            if curl -fsS http://localhost:5173 > /dev/null; then
              echo "dashboard serving after ${i}s"; exit 0
            fi
            sleep 1
          done
          echo "dashboard did not serve within 60s"; exit 1

      # The seeded demo task LEAVING `received` is what makes this a smoke test
      # of the ORCHESTRATOR rather than of two web servers: it means the
      # crystallizer, the interpreter and the autonomy engine all ran.
      #
      # NOT "reaches done". On a fresh clone the autonomy dial parks the golden
      # conversation at `awaiting_approval` for a human, by design — the
      # project's own end-to-end test (tests/test_executor_end_to_end.py:23-26)
      # has to POST /tasks/{id}/mode {"mode":"auto"} before it can assert
      # `done`. Asserting `done` here would fail the build on a correctly
      # working stack, and making the job POST that mode itself would have CI
      # drive the workflow rather than observe it.
      - name: Wait for the seeded demo task to leave `received`
        run: |
          for i in $(seq 1 120); do
            body=$(curl -fsS http://localhost:8000/tasks || echo '[]')
            if [ "$body" != "[]" ] && ! echo "$body" | grep -q '"state":"received"'; then
              echo "the demo task advanced after ${i}s:"; echo "$body"; exit 0
            fi
            sleep 1
          done
          echo "the demo task did not advance within 120s; tasks were:"

          exit 1

      # Always runs, so a failing assertion still leaves the logs behind — the
      # only way to diagnose a compose failure after the runner is gone.
      - name: Dump logs on failure
        if: failure()
        run: docker compose logs --no-color

      - name: Tear down
        if: always()
        run: docker compose down -v
```

## Self-review of this plan

Departures and risks, recorded so an executor is not surprised:

1. **The spec says the smoke job "waits on the compose health checks" (§6). That is imprecise** — only the `db` service declares one. The plan polls `/health` and `:5173` instead and does not modify `docker-compose.yml`. This is the plan correcting the spec, not disobeying it.
2. **Task 5 has a step an agent cannot honestly complete.** Confirming the dashboard *renders* requires a human. The plan says so explicitly rather than letting an executor claim a 200 response means the UI is right.
3. **Task 3's test passes on first run**, because it characterises existing behaviour. Its mutation step is therefore load-bearing, not a formality, and the plan says so.
4. **Task 1 is the phase's only production-code change**, and it touches all 24 settings. The regression net is 1038 tests on two databases; the failure mode is loud. `disable_startup` and `vision_enabled` are called out individually because their exact semantics (`== "1"`; `!= "off"`) are easy to lose in a mechanical rewrite — that would be a silent behaviour change, which is the thing this project has been bitten by most.
5. **Task 2 may surface a real Postgres migration defect.** That is the point of the task, not a blocker. The plan instructs the executor to report it rather than weaken a test.
6. **`_ENV_FOR` in Task 1's test duplicates knowledge held in `config.py`.** Deliberate: it is what makes the falsy-safe assertion walk every field rather than a hand-maintained subset, so a new field added with the wrong form fails on the day it lands. The duplication is the mechanism, not an oversight.
